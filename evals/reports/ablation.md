## 结论（怎么读这张表）

**1. 切块策略改的不是 Recall@5，而是"喂给模型的上下文完不完整"和"答案有没有原文依据"。**
Recall@5 四个策略落在 0.90–0.95，换算成题数只差 1 题（20 题里 structure 18 命中、其余 19 命中，
四策略共同失手的是 `-002`「董事会会议通知方式」），**这个差距在 n=20 下不构成结论**，
不能写"结构切块提升召回"。

差异明显的是另外两列：

- **Context Recall**：parent_child 0.95 > fixed / structure 0.90 > semantic 0.75。
  semantic 按语义断点切，容易把"条款一句 + 但书一句"切成两块，gold quote 只落在其中一块，
  父块/整节上下文不在池子里——Top-5 命中了、喂给模型的上下文却不完整。
- **Faithfulness**：structure 0.938 > semantic 0.892 > parent_child 0.880 > fixed 0.834。
  结构切块按"章 > 节 > 条款"切，上下文本身就是一条完整条款，模型复述时几乎不会越界；
  fixed 按页/窗口切，条款被页边界切断，模型只能靠拼贴，judge 能抓到无逐字依据的句子。

**2. 唯一一个"业务上会疼"的数字是 fixed 的 15% 误拒率**（20 条可答里拒了 3 条：`-002`、`-004`、`-019`）。
原因不是阈值，而是切块把条款切碎了、引用无法逐字定位 → `generate.py` 里"无有效引用即拒答"的兜底生效。
同一口径下 structure 是 0/20。这条链路能把"切块坏了"直接体现成"用户问不到"，是这套评测最值钱的地方。

**3. parent_child 的 P95 最低（73.5s）不能当成质量优势**：它召回池小、父块命中早，
但 faithfulness 反而比 structure 低（0.880 vs 0.938）——父块更长，模型在长上下文里更容易写出
没有逐字依据的连接句。延迟那几列在并行评测负载下主要反映排队，只能横向看，不要解释成 SLA。

**4. 成本几乎不受切块影响**（0.0009–0.0012 美元/问，含 judge）：差的是 completion token 长度，
不是检索成本；检索侧开销是本地 CPU 的 rerank（30 个候选/问，约 20s），不进 LLM 账单。

## 拒答阈值标定

误拒率 ≤ 15% 的前提下，取拒答准确率最高的阈值（宁可多拒，不可错答）

推荐阈值 **top_score ≥ -2.0**：此时无答案问题拒答率 100.0%、有答案问题误拒率 0.0%。

| -6.95 | 18.8% | 0.0% |

| -4.0 | 71.9% | 0.0% |
| -2.77 | 96.9% | 0.0% |
| 2.37 | 100.0% | 3.8% |
| 3.8 | 100.0% | 16.2% |
| 5.13 | 100.0% | 28.7% |
| 5.62 | 100.0% | 48.8% |
| 6.18 | 100.0% | 66.2% |
| 6.64 | 100.0% | 82.5% |
| 7.73 | 100.0% | 95.0% |

**标定结论**

- 本次 112 条样本上，可答题的 top_score 落在 **[1.38, 9.51]**，不可答题落在 **[-9.93, -2.07]**，
  两类之间有一段真实存在的空档。所以 `-2.0` 能同时做到"不可答 100% 拒"和"可答 0% 误拒"；
  空档内的阈值（约 -2.0 ~ 1.3）彼此等价，推荐点取在空档中间，不贴边。
- 但**阈值不是唯一的拒答防线**：当前代码默认值 `refusal_rerank_threshold = -6.0`，
  在 -6.0 处纯阈值规则只拒得掉 32 条不可答题里的 10 条（31%），实际拒答准确率仍是 100% ——
  其余 21 条是模型读了上下文后判 `not_found` / 引用校验不过而拒的（这 21 条多花了 21 次 LLM 调用，
  也是 181 次调用 > 80×2 的来源）。所以本次**不改线上默认值**：把阈值独自顶到 -2.0，等于让"检索分"单独承担拒答，
  语料一换成新文档、top_score 分布整体右移就会变成误拒。标定的价值是给出"阈值不敏感区间"，
  不是把默认值调到曲线最优点。
- 另修了标定函数的一个 tie-break 缺陷：原来在"拒答准确率 100%"的平台期按阈值从高到低取点，
  会选到 3.4（误拒 15%）这种被 -2.0（误拒 0%）严格支配的点；现在平台期取误拒率最低的点。

## 口径说明（补充，读数字前先看这几条）

- **样本**：87 条评测集里每策略取前 20 条可答 + 前 8 条不可答（确定性取前 N，四策略同一批题），
  共 112 次评测。**n=20 时 Recall@5 的粒度是 5 个百分点（1 题）**，1 题的差异不要当结论。
- **Recall@5 的分母**：只在可答题上平均。原 `aggregate()` 把 8 条不可答题也算进分母（记 0 未命中），
  把真实的 0.90–0.95 稀释成 0.64–0.68；已改为与 `context_recall` / `mrr` 同口径。
- **拒答准确率 / 误拒率**：前者分母是 8 条不可答题，后者分母是 20 条可答题；
  "拒答"包含三种成因（阈值、无有效引用、模型判 not_found），不是单一开关的行为。
- **Faithfulness / Answer Relevancy**：judge 与被测是同一个模型（`qwen-cn/qwen3.8-flash`），
  存在自评偏差，绝对值偏乐观；策略之间的相对排序比绝对值可信。
- **延迟**：P95 在 3 worker × 2 并发的评测负载下测得，含 reranker 排队，不等于线上 SLA。
  单问检索侧耗时主要是本地 cross-encoder 重排（30 候选 ≈ 20s CPU），不进 LLM 账单。
- **成本**：按 `config.py` 里的公开单价折算（prompt $0.15/Mtok、completion $0.47/Mtok），
  含 judge 那一次调用，所以是"评测成本"，线上单问会略低。

## 本次实验的执行配置（可复现）

- 数据集：`evals/datasets/qa_default.jsonl`，87 条（67 可答 / 20 不可答）；本次每策略取前 20 条可答 + 前 8 条不可答，合计 112 次「题 × 策略」评测。
- 四策略只改切块，其余链路完全一致：ACL → BM25 ∥ 向量 → RRF(k=60) → cross-encoder 重排(top 5) → 引用约束生成。
- 组件：embedding `BAAI/bge-small-zh-v1.5`、rerank `BAAI/bge-reranker-base`（均本地 CPU）、被测与 judge 模型同为 `qwen-cn/qwen3.8-flash`（本机网关）。
- 执行方式：`scripts/run_ablation_parallel.py --workers 3 --concurrency 2`（reranker 是进程级串行段，按策略切片多进程跑；逐题落盘，见 `evals/reports/_parts/`）。
- 耗时：LLM 调用 **181 次**、累计 **2294 秒**（并发等待前）；端到端墙钟 **1739 秒**。
- 冒烟：单策略 `--limit 15 --concurrency 6` 也跑通（structure：faithfulness 0.858 / Recall@5 修正口径后 0.917 / 拒答准确率 100%，墙钟 310s），与上表同量级，未纳入对比。
- **延迟口径**：表中的 P50/P95 是在上述并行评测负载下测到的（含 reranker 排队与并发生成等待），高于单用户串行体感；用于策略间横向比较，不等于线上 SLA。
- 单问成本按 `config.py` 里的公开单价折算（prompt $0.15/Mtok、completion $0.47/Mtok），含 judge 那次调用——所以是「评测成本」而非「线上单问成本」。
